## Goal

When a scoreboard read first shows (a) two teammates holding the same non-stacking effect, or (b) an enemy holding an item that can swing a fight if you don't know about it, the advisor says so, **scaled by how much it matters**:
a second Heroic Aura is a loud warning, a second Spirit Sap barely a note; a Refresher or a Curse on an enemy is critical. The mark stays on the hero's tile for as long as they hold the item, so a player who looks over
after the alert has gone still sees it, and it goes when the item is sold. Presentation only: no score changes (that is WP28 for allies and WP30 candidate 2 for counters).

## Why / premise check

1. **The ally half already exists, flat.** `MatchViewModel.TellOverlaps` raises one toast per newly shared effect (`TeamOverlap.Shared`, `ExplainText.SharedNotice`), and `MainWindowViewModel.TellOverlap` shows it for 8 s, and
   with *Sound on detect* on and another app in front plays the `NeedsLook` chime and flashes the taskbar ✔. Every shared effect is told the same way: no severity, nothing stays on screen after the toast, and nothing
   about enemies. This package replaces that path rather than adding a second one; the existing toast text stays the body of an ally alert.
2. **A restart tells everything again.** `_toldOverlaps` is an in-memory set that starts empty, so the first rescore after loading a saved match with builds re-announces every overlap it holds ✔
   (`MatchViewModel`, `_toldOverlaps`). Alerts must be told only for what a read brings in, and a loaded match is seeded silently.
3. **The ally data is only on the maintainer's machine.** `item_effects.csv` is generated by the sync and is not in `src/Assets/SeedData` yet ✔ (WP28 left the seed for the user to publish), and `TeamOverlap.For`
   returns `None` while `store.ItemEffects` is empty. Until the user publishes, installs get no ally alerts. This package does not publish; say so in the report.
4. **Severity for allies can be derived, not hand-kept.** What a duplicate wastes is the part of the second item's value that the first already gives, and a 6400-soul item wasted hurts more than a 1600-soul one: roughly
   `cost × (the overlapping part of the item's weight ÷ the item's whole weight) × coverage`, with the pieces already on hand (`OverlapCover.Coverage`, `OverlapWeights.Shape`, `WeightMatrix.OverlapSummed`, `item_stats`
   costs in `items.csv`). The user's two examples fix the scale: Heroic Aura (a 3200 weapon item whose value is mostly the aura) is bad, Spirit Sap (1600, one effect among others) is not a big deal. A hand override
   (below) catches what a formula gets wrong. **Print the derived table for every pair the data has and have the user confirm the thresholds before they are fixed** (as WP28 did for the stacking rules).
5. **Enemy threats are editorial and can't be derived.** Whether an item can "give someone two ultimates" or "take you out of the fight" is a judgement about the game, not a stat (`GameSync` throws such detail away on
   purpose). A small hand-kept file is the honest source, kept with reasons, like the sync's override sets. Items that exist in the seed today and are plausible entries (ids as in `items.csv`, effect not
   asserted here; **the user rates them**): `refresher`, `cursed_relic` (the user's "Curse": **confirm this is the item they mean**, the seed has no item named Curse), `silence_wave`, `silencer`, `disarming_hex`,
   `slowing_hex`, `knockdown`, `unstoppable`, `metal_skin`, `inhibitor`, `phantom_strike`, `ethereal_shift`, `rescue_beam`, `divine_barrier`, `lightning_scroll`, `echo_shard`, `magic_carpet`. `Debuff Remover` and
   `Soul Rebirth` are not in the seed ✔ (check `items.csv` again when starting; a patch may have added them).
6. **A false alert costs more than a missed one.** A read applies without review, and a toast for a Refresher the enemy doesn't have teaches the player to ignore all of them. The reader never wrongly identifies an item
   in WP24's corpus and about one cell in four reads as unknown at first, so alerts use only confident reads (`HeroBuild.ItemIds`), never an unknown cell, and a hidden or unseen cell (`CellKind.Hidden`, `Unseen`: the
   kill feed, a Street Brawl's enemy picks) is no evidence either way ✔ (WP26 notes). Measure on the Tab corpus (see Tests) before choosing how many sightings a Critical needs.
7. Re-check when starting: that `TellOverlaps` is still the only place that announces overlap, whether `item_effects.csv` has reached the seed (`rg item_effects src/Assets/SeedData`), and what WP31 has put on the match bar.

## Scope

Stages; stop at a stage boundary with a green commit.

**Stage 1: the finder, severity and the model file.**
- `item_alerts.csv` (a model file; hand-kept, with a header comment in `docs/publishing.md`, not generated): `item_id`, `kind` (`enemy_threat` or `ally_duplicate`), `severity` (`minor`, `major`, `critical`),
  `headline` (a short phrase finishing "…: " in the alert, for example "can reset an ultimate"), `counters` (item ids separated by `;`, optional), `note` (why, for the maintainer; never shown). An `ally_duplicate`
  row is an override of the derived severity; without one, the derived value stands. Load and save through `DataStore` like `item_effects.csv`; an unknown item id or severity is dropped with a log line, not a crash
  (a patch can retire an item).
- `ItemAlertFinder.For(store, match)` is a pure function of the store and `MatchState` (so tests and Model Health can call it) returning the alerts in force now:
  `ItemAlert(Kind, Severity, ItemId, Holders, Headline, Counters, Key)`. Enemy threats: each enemy's confident `ItemIds` found in the threat rows. Ally duplicates: `TeamOverlap.Shared()` entries with the derived or
  overridden severity. The key is stable per kind, item and holders, as `SharedEffect.Key` is.
- Severity of a shared effect is computed beside `TeamOverlap` from the data on hand (premise 4) and returned on `SharedEffect`; the thresholds are named constants with the user's confirmed examples as test cases.
- `AlertTracker` replaces `_toldOverlaps`: it keeps which keys have been told for this match, returns the *new* ones from each read, drops a key whose item is gone (sold, or a hero replaced) so a rebuy tells again,
  and is **seeded silently** by `Match` load, a Detect apply and a clear, so only what a Tab read brings in is announced (premise 2). Unit-tested without any UI.
- The settings: `AppSettings.ItemAlerts` (`Off`, `CriticalOnly`, `WarningsAndUp` (the default), `Everything`), in Settings → Detection, saying what each level does. It is the lowest severity that raises a toast; marks follow
  the same level, with *Off* hiding them. An older `settings.json` loads with the default.

**Stage 2: the marks and the report.**
- A **badge on the hero's tile** for each alert that hero holds an item in: an icon whose shape and a short word carry the severity (never colour alone), tooltip "Haze holds Refresher: can reset an ultimate. Seen 2 min ago.
  Counters: Debuff Remover." Two allies sharing an effect each get a badge naming the other. A badge stays while the item is held and goes when a read shows it gone; it names what it was read from.
- **One toast per read, not per item.** A read that brings in several alerts raises one toast headed by the most severe ("Critical: Haze holds Refresher") with "and 2 more" opening the list; Minor alerts never
  toast, they only mark. A Critical toast stays until dismissed or 20 s; Major uses the existing 8 s. The chime and window flash follow *Sound on detect* and *Window flash* exactly as `TellOverlap` does today, and only
  for Critical (today they sound for every overlap); a Major is silent. No other sound is added.
- **A "Notable items" list** (in WP31's flyout when it has landed, else a small flyout on the match bar): current alerts by severity, each with its holders, its age and a dismiss ("Got it" quiets that key for this match,
  kept in the saved match so a restart doesn't resurrect it). The count shows on the chip or the match bar.
- Accessible names and a polite live-region announcement for a new Critical; `AccessibilityTests` for the badges and the list.

**Stage 3 (optional; decide with the user after Stage 2):** counters in the results list. A row that is a listed counter of an alert in force gets a chip "Counters Haze's Refresher" (and a Match filter "Show counters
first" only if the user asks). Presentation only: **no score changes**, which are WP30 candidate 2.

Out: any effect on a score (a flat bonus is exactly what `docs/scoring_model.md` forbids); a sound for anything below Critical; alerts from anything but the confident reads of the scoreboard; guessing what an enemy
*will* buy; an overlay on the game; an editor page for `item_alerts.csv` (the file is edited by hand and published with `tools/PublishModel`, and an editor is a separate decision).

## Suggested design

- Alerts are derived state of the match (`ItemAlertFinder` over `MatchState`), recomputed on every rescore like `TeamOverlap`; only the *told* and *dismissed* keys are remembered. That keeps one source of truth and
  makes a hero swap or a clear drop the alerts by itself.
- A Critical needs the item confidently read; the minimum number of consecutive sightings (1 or 2) is decided from the corpus measurement, and the toast says "seen on the scoreboard" so a doubt is the player's to
  settle. If a later read no longer shows the item for that hero, the badge goes and the log says why ("Haze no longer shows Refresher").
- A freshly started session with a saved match seeds the tracker, then shows badges for what is held without toasting.
- Severity words and the three levels are the only vocabulary: `Minor`, `Major`, `Critical`; the derived ally severity maps into them with two thresholds.
- Colours come from `Palette` at 4.5:1; badges reuse WP31's pulse for the one-off glint, behind the same *Show read activity* setting.

## Acceptance criteria

- [ ] A Tab read that first shows two allies on Heroic Aura raises a Major or Critical alert; two Spirit Saps only mark (Minor) and raise no toast.
- [ ] A Tab read that first shows an enemy holding Refresher or the user's Curse item raises a Critical alert naming the hero and what the item does, and the hero's tile carries the badge until a read shows it gone.
- [ ] One read raises at most one toast; a restart or a loaded match raises none; a Detect apply or a clear starts clean.
- [ ] Only confident reads raise or keep an alert; the corpus check shows no false Critical.
- [ ] With *Item alerts* off there are no marks and no toasts; no score, ranking or explanation changes in any state.
- [ ] The chime and taskbar flash happen for Critical only, and only as *Sound on detect* and *Window flash* allow.
- [ ] The user has confirmed the severity thresholds and rated the starter threat rows; the seed is untouched.
